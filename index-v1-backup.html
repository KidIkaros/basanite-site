How it works

Three steps. No platform in the middle.

1

Seal

When you capture or finish a file, basanite seal binds its exact bytes into a signed manifest — Ed25519 + Falcon-1024, post-quantum from day one.

2

Edit

Every change appends a signed checkpoint. The edit history becomes part of the proof — deletions and rewrites are visible, not vanishing.

3

Verify

Anyone runs basanite verify — offline if they want. Signatures and hashes either check out or they don't. Three verdicts, no scores.

Straight answers

Questions this page would be incomplete without

Is this deepfake detection?

No. Detection guesses what a file is; basanite proves what happened to it. The two are complements. If a file carries no manifest, we say no-manifest — we don't pretend to know.

What if I lose my key?

The manifest stays verifiable — proofs don't die with the key. New work simply continues under a new key. There is no recovery server, by design.

Why not just use C2PA?

C2PA is a committee standard with a trust-list gate and documented security-goal failures in academic audit. basanite's format is independent and the verifier is free forever. Revocation is checked whenever a revocation journal is distributed with a file — and every verdict says plainly whether it was checked, never guessed.

Can someone cut my edit history down?

Signatures prove what they cover — so publishers announce their manifest head: basanite anchor file writes a signed announcement to post where attackers can't rewrite it (your website, a receipt, the work itself). Verifiers keep the .anchor file beside the file — or pass --expect-manifest-id — and any trimmed or substituted history fails with manifest-invalid (head-anchor). Without an anchor, a shortened history can only ever look like a shorter one — every verdict says so plainly instead of pretending otherwise.

Does the verifier phone home?

No. No telemetry, no account, no network call. Verification is local.
